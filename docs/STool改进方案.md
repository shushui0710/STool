# STool 改进方案（完全免费、离线优先、自己好用第一）

> 依据：2026-09-08 对 MTool 的调研（官网 + 本地安装包静态剖析，详见工作日志）。
> 定位修正：这工具首先是自己用的，**"好用"是最高优先级**；别人用着舒服是副产品，不做任何竞争/宣传导向的设计。
> 原则：**零付费、零强制联网、可还原、本地能力优先于云端服务**。
> 优先级：P0 = 下一步就做；P1 = 近期；P2 = 远期/评估。工作量：S ≈ 半天，M ≈ 1-2 天，L ≈ 3 天以上。

---

## 一、现状对照（STool 已有什么 / 差在哪）

| 能力 | STool 现状 | MTool 做法 | 差距本质 |
|---|---|---|---|
| 入口体验 | 拖入检测 → 手动选引擎 → 手动点能力按钮 | 拖入即自动完成全部设置 | 第一步摩擦 |
| 翻译方式 | 文本提取 CSV → 人工翻译 → 回填；JSON 注入（MV/MZ、Ren'Py、HTML） | 云端机翻一键完成 + 离线可用 | **缺免费机翻管线**（最大差距） |
| 引擎覆盖（翻译） | 改文件类：全；注入类：MV/MZ、Ren'Py、HTML | 运行时 DLL 注入，15+ 引擎 | 注入路线未走，但改文件路线覆盖了自己的大部分场景 |
| 修复能力 | 备份体系完善（.stool.bak） | RTP/DLL/中文路径/系统语言自动修复 | 修复未产品化 |
| 修改器 | 内存扫描 + MV/MZ 调试协议 | 同类 | 基本持平 |
| 生态 | GitHub 开源 | MCenter 社区分享修正包 | 缺分享格式与入口 |

## 二、改进项

### A. 体验与入口

**A1. 拖入即动的"快速行动"卡片（P0，S）**
- 做法：拖入游戏完成检测后，首页直接给出 1-3 张推荐动作卡片（如"这是 RPG Maker MV 游戏 → 开始翻译 / 改存档 / 解包"），一键直达对应页面；不改变现有手动流程。
- 理由：MTool 的核心体验就是"第一步零摩擦"。STool 检测结果其实已经算出来了，只差"替用户按下下一步"。

**A2. 环境预检前置（P0，S）**
- 做法：启动时与写操作前自检：① 输出/游戏目录写权限；② 目标文件是否被占用（如游戏运行中锁 exe）；③ 磁盘空间。失败时给出"原因 + 修复建议"（如"请关闭游戏后重试"）。
- 理由：MTool 启动 bat 就带写权限自检；STool 已遇过 LNK1104/文件锁类问题。报错从"失败后"移到"开始前"，是最便宜的用户好感。

**A3. 帮助文案结果导向 + 可搜索（P1，S）**
- 做法：帮助页改为纯文字（可 Ctrl+F），每个功能用"你能得到什么"开头（如"JSON 注入：翻译一次，永久离线，不改游戏文件"）；每页底部附等效 CLI 命令。
- 理由：MTool 教程的截图轮播是反面教材；文字可搜索、可维护、可翻译。

**A4. 版本更新提示（P2，S）**
- 做法：启动时用 GitHub Releases API 检查新版本，提示但不强制。
- 理由：免费且零成本，替代自动更新。

### B. 免费机翻管线（核心竞争力，最高优先）

**B1. "提取 → 机翻 → 回填/注入"全自动管线（P0，M）**
- 做法：新增"机翻"页：选翻译引擎 → 对已提取的 CSV（translation 列）批量机翻 → 用户抽查修正 → 一键"回填"或"JSON 注入"。进度可暂停/续翻（按行记录断点）。
- 理由：MTool 证明用户要的是"点一下就全翻完"。STool 的提取/回填/注入两头都已具备，缺的只是中间的机翻环节——这是投入产出比最高的一块。

**B2. 翻译引擎做成插件（P0，M）**
- 做法：定义 `Translator` trait（输入文本批次 + 术语表，输出译文），按注册表插件化。首批实现三个**免费**引擎：
  1. **用户自有 API Key**（DeepSeek / 智谱 / OpenAI 兼容接口）：用户自持 key，工具不代付费；STool 作者已有 DeepSeek 环境
  2. **本地模型**（Galgame 社区标准）：Sakura-13B / GalTransl 工作流（本地 Ollama / llama.cpp 的 OpenAI 兼容端点直接复用 1 的实现）
  3. **纯本地小模型兜底**（Argos Translate / NLLB，离线零依赖，质量一般但免费到底）
- 理由：对应 MTool 的"多专业翻译引擎"，但完全绕开付费订阅——本地模型 = 一次性下载永久免费；自有 key = 成本透明可控。机翻质量也随社区模型更新而提升。
- 注意：机翻只作为初稿，CSV/JSON 里人工可改，尊重"人工修正 > 机翻"。

**B3. 术语表/人名一致性（P1，S）**
- 做法：全局术语表 JSON（原文→统一译名，如角色名/地名），机翻时对全文做术语前置替换或作为翻译提示词注入。
- 理由：游戏翻译最大的质量痛点是人名漂移；实现成本低。

**B4. 断点续翻与增量更新（P0，S）**
- 做法：机翻按条记录状态（已翻/待翻/失败），中断后可继续；更新 JSON 时只翻新增原文，已有译文保留。
- 理由：对应 MTool"一次性完整翻译"；大游戏几万条文本，不能一次跑完。

### C. 注入覆盖扩展（按"自己玩的游戏"排序，先便宜后昂贵）

**C1. "译文/原文一键切换"——先用文件级方案解决 80% 的痛点（P1，S）**
- 做法：以封包为单位的"双档案切换"：翻译回填产出 `xxx.trans.xp3`（或 .rgssad 等）后，提供"切换到译文/切回原文"按钮（本质是重命名交换，原始档案始终原地保留）。
- 理由：不改原文件 + 随时切回原文，是注入方案最吸引人的体验；但这个体验**不需要进程注入也能得到**——文件交换就够了，成本只有半天。先把已支持引擎（吉里吉里、RGSS、MV/MZ、Ren'Py、Godot）都挂上这个开关。

**C2. 运行时注入实施（P1，L——AI 施工，按验证难度排序）**
- 做法：AI 直接实施，不再只做评估。顺序：**吉里吉里**（TJS 单一 VM、自己玩得最多、已有文本提取链路可对照验证）→ **RGSS**（Ruby VM、同有提取链路）→ **Wolf** → 其他。每步交付物：注入 DLL + 注入器 + "游戏内翻译开关"，配合本机真实游戏回归测试。
- 技术路线：Rust `cdylib` 编译 hook DLL（或必要处内联 C），标准 `LoadLibrary` 注入起步；hook 点优先选引擎的字符串/绘制 API 层；翻译数据复用现有 `stool_translate.json`。

### D. 修复能力产品化

**D1. "游戏跑不起来"体检（P1，M）**
- 做法：检测页增加"体检"卡片：① 系统区域/非 Unicode 语言是否为日文（RM 老引擎乱码根因）→ 给 Locale Emulator 建议链接；② MV/MZ RTP 缺失提示；③ 日文字体缺失（中文显示豆腐块的根因）→ 提示字体替换方案；④ 常见 DLL 缺失（d3d9/vcruntime）检测。
- 理由：MTool 把"智能修复"当四大卖点之一；STool 已有检测基础设施，补的是"诊断结论 + 建议"这一层。

**D2. 还原入口常在手边（P0，S）**
- 做法：封包/注入/存档每次操作完成后的提示里直接给"还原"按钮或命令（而不是让用户去翻文档）；首页给一句"所有修改自动备份为 *.stool.bak"。
- 理由：纯自己用的好的标准——改坏了三秒内能 undo，不需要记忆任何东西。

### E. 生态与迁移（零服务器）

**E1. 翻译包导出/导入（P1，M）**
- 做法：定义"翻译包"格式 = `stool_trans.json`（映射）+ `meta.json`（游戏名、引擎、版本、术语表），支持一键导出/导入；导入时自动匹配注入或回填。
- 理由：对自己首先就是**换机器/重装系统的翻译资产迁移**和防丢失备份；顺手也让人与人之间分享修正成为可能，不需要任何服务器。

### F. 工程

**F1. GitHub Actions CI（P2，S）**
- 做法：push 时自动 `cargo test` + release 构建，产物挂 Actions/Releases。
- 理由：自用阶段收益有限（自己本机构建更直接），开源协作多起来之后再上；先记着。

**F2. 移除已知噪音（P0，S）**
- 做法：修掉 `marshal.rs` 的 unused_comparisons 警告；清理 README 中已过时的描述（如测试数与实际保持同步）。
- 理由：零成本提升"维护良好"的第一印象。

## 四、注入路线的重新评估（AI 施工前提下的修正）

> 修正说明：初版方案按"人来写代码"估成本，得出"不追全引擎注入"。用户定调：**实现由 AI 完成，时间/技术人力成本不构成约束**。那么成本论据作废，剩下的真实约束只有三个：**验证难度、稳定性风险、维护面**。结论随之改变——注入路线值得做，但要按"验证难度"排序推进。

**AI 施工后仍然真实的约束：**

1. **验证闭环依赖真机**：注入代码 AI 可以直接写，但"hook 是否命中、游戏是否被带崩"必须在真实游戏进程上验证。STool 工作区里就有真实游戏（BLACK SOULS II 的 .rgss3a、多款吉里吉里游戏），可以启动游戏+注入实测——所以验证是**可行的**，只是迭代轮次多、部分环节需要用户配合跑游戏看现象。这不是"做不做得到"，是"来回试多少轮"。

2. **杀毒软件误报**：注入 DLL + 远程线程几乎必触发报毒。自用场景下解法廉价：给目录加白名单即可。只有将来分发给陌生人时才变成真问题（签名/分发渠道），现在不用管。

3. **维护面 = 引擎版本碎片化**：MTool 的 38 个 loaders 文件就是多年适配的实体。AI 施工大幅降低"追新版本适配"的成本（每个新版本是一次针对性分析任务，而非人力恐慌），但这块是长期存在的"账"，不是一次性的"活"。

**排序逻辑（替代原来的机会成本论证）：** 成本≈0 之后，决策依据变成——
- ① 验证难度（能否在本机自动化/半自动化测试）
- ② 对自己游玩引擎的覆盖增量
- ③ 崩溃风险（hook 失败是否只影响翻译不影响游戏）

由此得出顺序：**吉里吉里（TJS 单一 VM、自己玩得最多、已有完整文本提取链路可对照）→ RGSS（Ruby VM、同样已有提取链路）→ Wolf → 其他**。MV/MZ、Ren'Py、HTML 已完成注入。

**结论（修正版）**：注入路线从"远期评估"提为"中期主线"，与机翻管线并行推进。C1 双档案切换保留——它半天就能用，且注入做好之前它是唯一的"切回原文"体验。

## 五、为什么不直接全引擎注入（初版论证存档，供对照）

> 以下为"人工施工"前提下的论证，在 AI 施工前提下其中 4、5 两条（需求盘点、机会成本）仍部分成立，1-3 条的时间/人力成本大幅弱化，保留作为背景。

1. **每个引擎是一个独立的原生逆向工程**
   - `RGSSHook64` hook 的是 Ruby 解释器内部（字符串创建/绘制调用），不同 RM 版本（XP/VX/Ace）、魔改运行时（mkxp-z）内部结构都不同；
   - `krkr2Hook`/`krkrzHook` hook TJS 虚拟机，还需配套 `tjsjson32/64` 处理数据序列化；
   - `wolfHook` 对 Wolf 自研脚本 VM，官方宣称"1.00 至最新版本"都支持——意味着每个引擎版本都要追着适配。

2. **注入基础设施本身是一个专项**
   - 进程注入器、权限提升、32/64 位双编译、"注入失败不能把游戏带崩"的可靠性；
   - 杀软误报是注入类工具的长期问题（自用场景可加白名单解决）。

3. **与 STool 的技术栈错位**
   - STool 的积累在纯 Rust 文件格式解析（无外部进程、好测试）；注入是 native/FFI/内存布局的另一个学科。

4. **需求增量有限**：吉里吉里、RGSS 已有完整"提取→翻译→回封"链路且真机验证过；注入的增量是"零文件改动 + 免回封"。

5. **机会成本**：人工施工前提下，机翻管线的收益覆盖面更大。

## 六、不做什么（明确边界）

- **不做云端服务/账号体系**：与"完全免费"冲突，机翻全部走用户自有 key 或本地模型
- **不做非法解密**：保护类加密（Hxv4 等）维持现有明确报错立场
- **注入不再设"做不做"的门槛**，只按验证难度排顺序
