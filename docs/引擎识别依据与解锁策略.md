# 引擎识别依据与解锁策略

> 生成时间：2026-09-10 ｜ 对应实现：`src/engines/recognize.rs`（识别）、`src/features/unlock.rs`（解锁）、
> `src/features/guard.rs`（反修改保护识别，见 §7）
>
> 本文件是**检测层与解锁层的单一事实来源**：改识别判据或解锁策略时，**同步改这里**。
> 文档里的引擎顺序与 `UNLOCK_CATALOG` 一致，可直接对照代码。

---

## 0. 两层架构

```
① 检测层：ScanCtx（1×read_dir + 1×walkdir）──► 各插件/识别器打分 ──► Detection{score, evidence}
                                                                     │ score ≥ 60 才算"确认识别"
② 解锁层：UnlockSpec 策略表（按 engine_id 查）──► pick_route ──► 六类手段之一
```

- **检测**只用 `ScanCtx` 的内存索引，**零额外 IO**（`Engine::detect_scan` 不得自己遍历目录）。
- **解锁**只用声明式策略表 + 统一调度器；引擎私有实现走 `Engine::unlock_impl(route, ctx)`。
- 两者都以 `engine_id` 为键，新增引擎时**各改一处 + 各加一行**。

## 1. 检测层

### 1.1 判定线与置信度

| 分数 | `Confidence` | 含义 |
|---|---|---|
| ≥ 85 | 高置信 | 特征齐全，基本不会错 |
| 60–84 | 已确认 | `DETECT_LINE = 60`，确认识别 |
| 30–59 | 疑似（证据不足） | 会附"差 N 分未达判定线"提示 |
| < 30 | 未识别 | 不出现在结果里（0 分被过滤） |

排序键：`(score, plugin.priority)` **降序**。识别器（盲区引擎）的 `priority` 一律 < 60，
保证同分时**正式引擎优先**（已有单测 `test_recognizer_priority_below_real_engines` 守住）。

### 1.2 判据库（`recognize::Sig`）

| 判据 | 命中条件 | 数据来源 |
|---|---|---|
| `Ext(e)` | 任意位置存在 `*.e` | `ext_count` |
| `ExtAny([e…])` | 存在任一扩展名 | `ext_count` |
| `ExtN(e, n)` | `*.e` 数量 ≥ n | `ext_count` |
| `ExtSum([e…], n)` | 这些扩展名数量之和 ≥ n | `ext_count` |
| `RootFile(f)` | 根目录一级存在 `f` | `root_files` |
| `RootFileEnds(sfx)` | 根目录一级存在 `*sfx` | `root_files` |
| `RootDir(d)` | 根目录一级存在 `d/` | `root_dirs` |
| `RootDirEnds(sfx)` | 根目录一级存在 `*sfx/` | `root_dirs` |
| `Dir(d)` | 任意深度存在 `d/`（≤5 层） | `dir_names` |
| `DirEnds(sfx)` | 任意深度存在 `*sfx/` | `dir_names` |
| `FileNamed(f)` | 存在 `f`：根目录一级 **或** `NOTABLE_FILES` 白名单（任意深度） | `root_files` + `notable_files` |
| `ExeContains(sub)` | 根级 exe 名含 `sub` | `exes` |
| `ExeAnyContains([sub…])` | 根级 exe 名含任一 `sub` | `exes` |
| `NumberedVol` | 存在"分卷"（扩展名为 3 位数字，如 `x.pfs.000`） | `ext_count` |

> `NOTABLE_FILES`（`engines/scan.rs`）是"埋起来的强特征"白名单，匹配全名（大小写不敏感）：
> `actors.json`、`assembly-csharp.dll`、`gameassembly.dll`、`project.godot`、`config.tjs`、
> `startup.tjs`、`data.win`、`gameexe.dat`、`gameexe.ini`、`seen.txt`、`tyrano.js`、`main.lua`、
> `bregexp.dll`、`bgi.gdb`、`libcocos2d.dll`、`rpg_rt.exe`、`nscript.dat`、`arc.nsa`、`system40.exe`。
> **新增白名单条目 = 扩大 `FileNamed` 的表达力**，改 `scan.rs` 一处即可。

### 1.3 打分原则

- **强特征单独过线**：专有文件名 / 扩展名（`.mjo`、`.ypf`、`data.win`、`BREGEXP.DLL`）给 ≥ 60 分。
- **弱特征必须组合**：`.arc`、`.pak`、`.dat`、`.pfs` 这类"谁都在用"的，单条给 20–45 分，靠组合过线。
- **消歧**：`.pfs` 同名于 BGI 与 Artemis —— **原生 `artemis` 插件优先级更高（70）**，
  以「`.pfs` 真实可解析（`pf6`/`pf8` 头 + 索引校验通过）+ `.asb`/`.ast` 伴随文件」为准；
  `.pfs` 单条 30 分只作盲区识别器里的弱证据，靠组合过线。
- **升级为原生插件后要清理旧识别器**：`artemis` 从"盲区识别器"升级为原生插件（真解包/回封）时，
  必须删掉 `recognize.rs` 里的同名条目与该条目的测试断言，否则 id 冲突 / 双份打分。
- **打包方式 ≠ 引擎身份**："有 `app.asar`（Electron 打包）"是**打包/加载方式**的线索，不是引擎的线索。
  `HtmlGamePlugin` 曾把"有 asar"当成引擎证据（70 分），于是**打包在 asar 里的 TyranoScript 游戏**
  被误判成 `html_game`——因为检测只扫游戏根目录，看不见 `app.asar` 里有什么。
  修法见 §1.4。

### 1.4 封包内探测（`probe_asar`）——「检测零额外 IO」的唯一例外

`ScanCtx::build` 的硬规矩是"检测零额外 IO"（1 次 `read_dir` + 1 次 `walkdir` 收齐，见
`ARCHITECTURE.md`）。**`probe_asar` 是唯一一处刻意的例外**，用于解决上面那个"看不见封包内部"的盲区：

- **触发**：仅当根目录 `ext_count("asar") > 0` 时才探测，只读**头部 JSON**（条目名清单），
  **绝不读数据区**；条目名上限 `ASAR_ENTRY_CAP = 20_000`，超出即 `truncated`。
- **产物**：`AsarEntries { path, names, total, truncated }`，对外只暴露 `has_prefix` /
  `ext_count` / `has_name` 三个谓词——判据写法与 `ScanCtx` 其余部分保持一致。
- **单点**：`scan::asar_candidates(root)` 是"去哪找 asar"的**唯一实现**，`inject.rs` 的
  `asar_candidates` 已改为转调它（此前各自抄过一份）。
- **打分收敛**（`others.rs`）：
  - `TyranoPlugin`：`asar.has_prefix("tyrano/")` 给 **75 分**（> `HtmlGamePlugin` 的 70），
    另对 `ext_count("ks")`（15）/ `data/scenario/`（10）/ `Config.tjs`（10）加分；
  - `HtmlGamePlugin`：同一条 `asar_has_tyrano` 线索反过来**让位**（note 写"asar 内含 tyrano/
    运行时，判定交由 TyranoBuilder 插件"），避免两个插件对同一份证据给出矛盾结论。
- **真机验证**：`NTRdemic〜…〜`（Electron，`resources/app.asar`）此前报 `html_game 70`，
  现在报 `TyranoBuilder / TyranoScript [tyrano] 110 分 · 高置信`，证据为
  "app.asar 内含 tyrano/ 引擎运行时；app.asar 内 42 个 .ks 剧本；app.asar 内 data/scenario/
  剧本目录；app.asar 内 Config.tjs"。
- **注意**：`install_tyrano` 对"asar 内的 Tyrano"**刻意复用 `install_html` 的 hook 与管道**
  （已真机验证生效，见 `test_install_tyrano_into_asar` 钉死"同一份 hook 字节"这一不变量），
  而非切到 `tyrano.js`——两个 hook 的差异（jQuery 包装、trim 兜底、同步/异步 XHR）留待后续收敛，
  避免把已跑通的游戏改回坏。

## 2. 解锁层

### 2.1 六类手段（`UnlockRoute`）

| key | 手段 | 自动 | 说明 |
|---|---|---|---|
| `bundled` | 替换自带全CG存档 | ✅ | 把游戏目录里自带的「全CG存档」按同名复制进存档目录。**与引擎无关**，最省事、成功率最高 |
| `ingame` | 游戏内全开开关 | ❌ | 设置 / 隐藏界面的 toggle，只能提示用户去找 |
| `config` | 改配置文件开关 | ✅ | json / ini / xml / txt 里的解锁开关 |
| `registry` | 改注册表键位 | ✅ | Unity PlayerPrefs `<键>_h<djb2 哈希>=1` |
| `savefile` | 改存档里的标志位 | ✅ | 存档里的位标志 / 开关 / 计数：Ren'Py pickle `persistent`、**RPG Maker MV/MZ 的 `switches`**（见 §3.1.1） |
| `manual` | 人工分析 | ❌ | Cheat Engine / 内存 hook |

### 2.2 路线选择（`pick_route`）

优先级从高到低：

1. **`--opt:route=<key>` 显式指定**（写错 key 直接报错并列出合法值，不静默回退）；
2. **带 `--opt:restore=`** → 用该引擎的首选（引擎私有）路线（目前仅 Unity 支持还原）；
3. **发现「自带全CG存档」** → `bundled`（覆盖引擎自身偏好：能"复制存档"就别"改存档"）；
4. **否则** → 策略表第一条（引擎首选）。

### 2.3 安全设计（这是功能能用的前提）

| 机制 | 实现 |
|---|---|
| **默认只读** | 不带 `--opt:apply=1` 只预览，**不写任何文件 / 注册表** |
| **备份不可覆盖** | 覆盖任何文件前 `settings::backup_once()`（已存在即返回，绝不覆盖），可用 `stool restore` 还原 |
| **来源≠目标** | 「自带全CG存档」目录被排除出候选**目标**目录（否则会"复制到自身"） |
| **不猜关键路径** | 找不到存档目录时**拒绝落地**并提示 `--opt:save_dir=`，而不是把存档丢进游戏根 |
| **诚实告知** | 引擎无内置实现的路线直接报"没有内置自动实现 + 该怎么做"，不假称成功 |
| **注册表侧** | 哈希自检（用现存键反推）、非 `REG_DWORD` 跳过、裸值跳过、写后读回校验（见 `gallery.rs`） |
| **启发式闸门** | 精确来源读不到、又无现存键族可收敛时，候选只能从场景/资源二进制里捞 —— 此时**默认拒绝写入**，必须显式 `--opt:force_heuristic=1`。只读预览不受影响。 |
| **能撤销** | `--opt:undo=1` 删掉「本工具会写的候选键」（默认只预览、`--opt:keep=` 护真键、删前整键快照）。**重跑一次不会报错**（删除幂等） |
| **点名写入** | `--opt:set=名称=值,…` 只写点名键、不猜；类型按现存值走（字符串仍是字符串）；任何一条入参不合法就**整体中止**，不留半截状态 |
| **键名看得见** | 界面「进阶」里可**列出注册表现存的全部键**（键名 / 当前值 / 类型），点一行把键名填进按名写值框 —— 用户不必猜键名。只读，且引擎自身的键（`unity.*` / `Screenmanager *`）单独归一组提示「别动」 |
| **假成功不留** | 候选「本来就全是 1」时明说「这多半是上次本工具写的，不代表已解锁」，不把 `files_done=0` 粉饰成成功 |
| **区分「设置文件」与「进度存档」** | 自带包里可能**只有设置文件**（如 KKC4 的 `System.bin` = 音量 / 跳过 / 已读记录），而 CG 标记在 `data*.bin` 的 `mNNN_NNFlag` 字段里。覆盖设置文件**解不开 CG** —— 这种情况必须直说，不能让人以为跑完就好了 |

### 2.3.1 「自带存档」怎么被找出来（`find_bundled_saves` / `find_save_dirs`）

这一层的**唯一原则：来源谓词必须只有一份**。历史上 `find_bundled_saves`（找来源）与 `find_save_dirs`（找目标）
各写了一份目录名判断，于是 `C0771存档` 这种目录**同时**是「来源」和「目标」——「复制存档」变成「复制到自己」。
现在两者共用 `is_bundle_dir_name()`：

```text
is_bundle_dir_name(name)
  ├─ 命中 NOT_BUNDLE_DIR（backup/备份/素材/resource/assets/log/cache） → false
  └─ 命中 BUNDLE_DIR_KEYWORDS（全cg/cg存档/全开/全解锁/完全存档/100%/回想/回廊/セーブデータ）
     或 泛化规则 is_archive_dir_name（名字以「存档」结尾且长度 ≥2，如 C0771存档）
     → true
```

| 规则 | 说明 |
|---|---|
| **通用存档目录名** | 发行商常用「同人社团编号 + 存档」（`C0771存档`）。不靠关键词表，靠 `存档` 后缀兜住 |
| **嵌套深度 8 层** | 打包者习惯套多层：`C0771存档/C0771存档/存档/…` = **depth 4**。旧 `max_depth(3)` 永远看不到；现与来源扫描统一为 **8** |
| **`位置.txt` / `说明.txt` 优先** | 打包者写的目标路径说明，比任何名字启发都准。取**第一行像绝对路径**的（盘符 + `:` + `\`/`/`），忽略正文 |
| **用户名占位符展开** | `（用户名）` / `(用户名)` / `<用户名>` / `{用户名}` / `%USERNAME%` → `$USERNAME` |
| **解码只能靠 GBK** | `encoding_rs::GBK.decode()` 的 `ok` 是**陷阱**：只要有一个字节不可映射就返回 `false`，但其余字节其实全对。若据 `ok` 回退到 `from_utf8_lossy`，中文全部变 U+FFFD → 占位符匹配不上 → 路径作废。**必须无条件采用 GBK 的结果** |
| **游戏根不算存档目录** | 根目录进了候选会被当目标，导致存档写进游戏根 |

### 2.4 Unity 注册表路线的「键名从哪来」

注册表路线要写 `<原始键名>_h<djb2>`，**难点全在"键名是什么"**。本工具分两级来源：

| 级别 | 来源 | 实现 | 适用 |
|---|---|---|---|
| **精确** | Mono 版：`*_Data/Managed/Assembly-CSharp*.dll` 的 `#US` 堆 | `formats::dotnet`（PE → CLI 头 → 元数据根 → 流头，读 `#US`/`#Strings`） | Mono 版 Unity |
| **精确** | IL2CPP 版：`*_Data/il2cpp_data/Metadata/global-metadata.dat` | `formats::il2cpp`（magic `0xFAB11BAF` + v24..31 + 三区首尾相接校验） | IL2CPP 版（**无 C# 程序集**） |
| **兜底** | `<*_Data>/level*`、`sharedassets*`、`resources.assets`、`globalgamemanagers` 里的 ASCII 串 | `scan_scene_strings`（`looks_like_key` 过滤） | 两者都读不到时 |

**都不需要反编译器 / .NET 运行时**：`PlayerPrefs.SetInt("cg_flag_01", 1)` 里的字面量就躺在元数据字符串堆里，
直接读即可。实机效果（Yakuzarogue / IL2CPP v31）：直接列出真实键 `cg_button_name1`…`cg_button_name7`。

**噪声处理**（IL2CPP 字面量池里绝大多数是引擎/框架串）：

- `looks_like_key` 白名单字符集 `[A-Za-z0-9_ .-]` + 非 ASCII；首末字符必须是字母/数字/`_`；
  禁连续空格；剔除 base64 常量块（protobuf 描述符等长串）；
- `sort_candidates` 按"像不像画廊键"分层（`cg_`/`CG01`/含 gallery 关键词 → 有下划线 → 其它），
  **先排序再截断**，避免真键被字典序挤出 `max` 之外；
- 只读入口 `stool cg-candidates <游戏目录>` **完全不碰注册表**，可反复查看；写入时才走
  `unlock --opt:apply=1`（写前快照、写后读回校验、`--opt:restore=` 还原）。

### 2.5 CLI / GUI

```bash
# 只读预览（缺省）：列出该引擎可用手段 + 自带存档候选 + 存档目录
stool unlock "D:/Games/某游戏"

# 落地（自动选路线：有自带存档优先用它）
stool unlock "D:/Games/某游戏" --opt:apply=1

# 指定手段 / 指定目标目录
stool unlock "D:/Games/某游戏" --opt:apply=1 --opt:route=registry --opt:filter=CG
stool unlock "D:/Games/某游戏" --opt:apply=1 --opt:route=bundled --opt:save_dir="D:/Games/某游戏/SaveData"

# 查能力矩阵 / 查解锁策略表
stool engines            # 每个插件的 能力 + 识别依据 + 解锁动作 + 手段优先序
stool unlock-support     # 全部引擎的解锁策略表
```

GUI：资源解包页的「解锁辅助」按钮 → 「全 CG 解锁」面板（手段下拉 + 只读预览开关 + 键名过滤）。

#### 3.1.1 `rpgmaker_mv` 的 `savefile` 路线（2026-09-27 新增，`engines/others.rs::unlock_switches`）

**为什么之前点不动。** 策略表原来是 `bundled` > `config` > `ingame`，三条全断：目录里通常**没有**自带全CG存档 →
第一条报「未发现自带全CG存档」；`config` 没有私有实现 → 报「『改配置文件开关』手段没有内置自动实现」。
而这游戏的解法是**确定**的（`data/System.json` 的开关表 + 存档里的 `switches`），只是没人实现。

**开关名从哪来。** `data/System.json` 的 `switches` 是 `[null, "名前", …]` 名表，**下标 = 开关 ID**。
本工具在其中匹配解锁词，**不猜 ID**。词表按真实名表调过（实测 81 个开关名）：

| 词表 | 命中 | 备注 |
|---|---|---|
| 缺 `解放` | **漏掉 66 `ハード済／７解放`、67 `コンプ済／８解放`** | 只靠 `ギャラリー`/`アンロック` 不够 |
| 含 `解放`（现用） | **10/10 命中，0 误报** | 词表：`ギャラリー` `gallery` `回想` `リコレクト` `recollect` `album` `アンロック` `unlock` `解放` `cg解放` `全cg` |
| 再加 `済` | 多出 2 条误报（68、76，是玩法标记不是画廊） | 故**不含 `済`** |

**存档两种布局都要认**（`MzSwitchLayout`）：

| 布局 | 出现的文件 | `switches` 形状 | 处理 |
|---|---|---|---|
| `Indexed` | 进度存档 `fileN.rmmzsave` | `{"_data":[null,false,true,…]}`，**下标 = ID** | 越界时**扩容补 `null`**（`_data` 长度即数组长度，绝不能静默丢弃） |
| `Entries` | `shared.rmmzsave`（插件 `DarkPlasma_SharedSwitchVariable`） | `[{"id":65,"value":true},…]` | **只改已存在的条目**，不给插件塞它没注册的开关 |

**MZ 存档磁盘格式有个必须绕过的坑**（`saves.rs::mz_unwrap` / `mz_wrap`）：
`rmmz_managers.js` 存盘时是 `pako.deflate(json, {to:"string", level:1})` 再 `fs.writeFile(path, zip)` ——
「binary string」被按 **UTF-8** 写出，于是**每个 ≥ 0x80 的字节膨胀成 2 字节**（`0xAD` → `C2 AD`）。
游戏自己回读没问题，但**外部 `zlib.inflate` 恒定失败**（`corrupt deflate stream` / `invalid distance too far back`），
且文件头仍是正常的 `78 01`。实测：直接 inflate **5/5 失败**，先 `mz_unwrap` **5/5 成功**。
**这个包装是 MZ 原生的，不是加密、不是这家游戏特有** —— 所以 `saves.rs` 读写两侧都做 unwrap/wrap，
避免「读出来了但写回去变成裸 zlib → 游戏打不开」。回归素材见 `tests/fixtures/mz_save/`。

1. **`engines/scan.rs`**：若强特征埋在子目录，把文件名加进 `NOTABLE_FILES`。

## 6. 已知局限

- **Unity 注册表路线的候选键名**：Mono 版走 `Assembly-CSharp*.dll` 的 `#US` 堆、IL2CPP 版走
  `global-metadata.dat` 的字面量池，**都是精确字符串**；但 IL2CPP 池里引擎/框架串占绝大多数
  （实测 5000–9000 条），故仍可能混入无关名字。已用字符集白名单 + base64 常量块剔除 + 相关性排序
  缓解（见 §2.4），工具会报出"高置信候选"条数；**最稳的仍是优先找游戏自带的「全开开关」**。
  若某游戏的字面量被运行时解密（如 Beebyte 之类混淆），元数据里读不到真键 —— 此时会明确退回
  启发式路径并如实说明，而不是假装成功。
- **IL2CPP 元数据只支持 v24..31**：区间外（或布局校验不通过）直接退回启发式，不去猜偏移。
- **`bundled` 路线依赖"游戏跑过一次"**：存档目录通常是运行时生成的；没生成时需显式 `--opt:save_dir=`。
- **`config` / `savefile` 对多数盲区引擎只有指引**：这些引擎的存档格式未公开，自动改动风险高，故只做诚实提示。
- **`manual`**（Cheat Engine / 内存 hook）不自动化：越界且不可靠。
- **分卷检测是"宽松"的**：任何 3 位数字扩展名都会命中 `NumberedVol`，故它只给 45 分（必须与 `.pfs` 组合）；
  Artemis 分卷封包（`x.pfs.000`）本工具**不支持拼接**，只识别并给替代做法。

## 7. 反修改保护识别（`features/guard.rs`，内存层）

与上文「文件层引擎识别」正交：这一节处理的是**游戏运行时对内存数值的反修改保护**，
入口是 `stool guard <pid> --opt:addr=…`（诊断一个地址）与 `stool guard-regions <pid>`（看页保护分布）。

### 7.1 五种保护形态与对应判据

| 保护形态 | 现象 | 判据（guard 实测得到的事实） | 对应方案 |
|---|---|---|---|
| **周期性 / 延迟回滚** | 改完过一瞬又变回去 | 每轮写入"存活"时长 `Verdict::{Periodic,Delayed}`；多轮存活一致 → `Periodic` | 自适应锁值（按实测间隔设周期）；根治走代码补丁 |
| **立即回滚** | 改完几乎没停住 | 全部轮次存活 <1ms 且**没有一轮活满窗口** → `Instant`；此时不给锁值方案（压不住） | 代码补丁 / 改数据源 |
| **页只读 / Guard** | 写不进去（像"改了没反应"） | `RegionStat.protect` 的 `is_directly_writable` 为假 | 强制写入（`force_write_raw` 临时解保护）|
| **派生 / 缓存副本** | 写了也没用，值由别处推导 | 两次写入差分命中 `Rewrite::{Xor,Shift,Constant,Opaque}` | 改数据源（收敛同值候选后逐个反测）|
| **代码层还原** | 有专门指令把值写回 | 可执行区扫到 `mov [disp32], imm32` 且立即数 == 原值/目标地址 | 代码补丁（改立即数或 NOP）；找不到落点时给 CE 硬件断点路线 |

### 7.1.1 数据源反测的安全约束（`pick_writable_mirrors`）

同值副本可能有几十个，逐个写探测值去试「写谁会让目标地址跟着变」是找数据源的关键一步，
但不能乱写：

- **只试「页保护允许直接写入 且 不可执行」的副本**：只读页（代码段 / 常量 / 映像数据）几乎
  不可能是游戏变量；**可执行且可写**的页（JIT / 自修改代码）往里面写探测值风险太大。两类都排除。
- **每试一个立刻恢复**原值（普通写失败时兜底再走一次 `force_write_raw`），不把探测值留在别人数据上。
- **最多试 [`MAX_SOURCE_TRIES`] = 24 个**可写副本；一个都没试成（全是只读/可执行页）时，报告里
  明确写出「都不在可写的普通数据页上，未做写入反测」，而不是假装没找到源。

### 7.2 保护机制线索（模块名单 / 导入表）

- **已加载模块**（`MODULE_TABLE`，按 `MODULEENTRY32W.szModule` 匹配）：
  `EasyAntiCheat` / `BattlEye` / `Vanguard` / `ACE` / `nProtect` 等 → `Family::OnlineAntiCheat`；
  `Themida` / `VMProtect` / `UPX` / `Enigma` / `ASProtect` 等 → `Family::Packer`；
  若干本地 DRM 模块 → `Family::LocalDrm`。
- **PE 导入表反调试 API**（`ANTIDEBUG_IMPORTS`，解析主程序导入表）：`IsDebuggerPresent` /
  `CheckRemoteDebuggerPresent` / `NtQueryInformationProcess` / `NtQueryObject` /
  `OutputDebugStringA/W` 等。
  **注意**：这些 API 普通程序（CRT / 运行库）也常导入，故**默认标注为低置信度线索**——
  只有同时命中"已加载模块里有加壳 / DRM"或"写入被立即还原"时才有参考价值。

### 7.3 边界（硬性）

- **只诊断本机单机游戏**；识别到在线反作弊只给风险提示，**不提供任何绕过**（与 §7 数据与安全边界一致）。
- 探测只写**探测值**（默认自动构造，如原值 100 → 探针 1100），每轮结束**恢复原值**，不留持久副作用。
- 判定阈值由真机校准（`scripts/mock_mem_guard.py` 靶子 + `scripts/_guard_smoke.sh`），
  合成数据不作为定案依据。

### 7.4 真机验证结果（受控靶子进程）

| 靶子模式 | 模拟的形态 | guard 判定 |
|---|---|---|
| `none` | 无保护 | 稳定（写入被保持）→ 提示"改了没用来自别处" |
| `periodic` | 10ms 周期回写 | 周期性回滚 → 自适应锁值 1ms |
| `fast` | 1ms 高频回写 | 周期性回滚（间隔 1.5ms）→ 自适应锁值 1ms |
| `readonly` | 只读页 | 页只读 → 强制写入 |
| `constant` | 只读页 + 1ms 自写回 | 页只读 + 周期性回滚 → 强制写入 + 锁值 |
